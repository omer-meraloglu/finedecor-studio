# Architecture and schema

The app uses server-rendered localized Next routes with a client library shell. The DOM catalog is rendered immediately from a source-reviewed snapshot, then refreshed from `/api/catalog`. Three.js is isolated in `components/scene-view.tsx` and imported only after explicit 3D intent. Product pages keep their source swatch in 2D; **Inspect in 3D** navigates to `/{locale}/studio?variant={exactID}` rather than embedding another Studio. A valid linked variant overrides the restored device study with a fresh Kitchen study, starts 3D even after a previous 2D choice, and leaves the separate shortlist intact. Plain Studio visits restore the existing device study and visit preview preference. Studio uses the shared material records and validated project state. The local design uses the provided original logo and authorized source photos.

`lib/model.ts` defines every requested entity. `lib/schema.sql` implements ProductFamily, Decor, Finish, ProductVariant, Application, MediaAsset, MaterialAsset, TechnicalDocument, ClaimEvidence, Project, SampleRequest, Office, NewsArticle and UserRole, plus explicit VariantApplication joins, ShareToken, ContentRevision, AuditEvent, RateLimit and Outbox. Foreign keys, `(decor_id,finish_id)` uniqueness and stable IDs prevent synthesized combinations. Unknown SKU/family/dimensions remain null. JSON payload columns retain typed revisioned content while relational keys protect critical relationships. Existing production PIM has not been supplied.

`lib/store.ts` owns a Node SQLite connection. Development schema setup is intentionally idempotent; a real deployment must replace initialization with versioned migrations and backups. Product source records are immutable seed references. Editorial revisions are separate; technical approval is distinct from source verification. Production variant publishing and fulfilment remain blocked until a complete owner-approved import.

Project payload contains only the whitelist validated by Zod. Server ownership uses a SHA-256 hash of a 256-bit HttpOnly session capability. A project is an immutable saved snapshot; editing requires a new save and clears enquiry association. Share tokens are 256 random bits, stored as hashes, expire in 30 days and can all be revoked for a snapshot. No owner capability, contact data, enquiry reference or role token is included in share payloads.

Request and Contact share `components/enquiry-form.tsx`, with the current persistence capability supplied by the library shell. Both validate the same strict enquiry schema. Request carries the exact selected variant IDs and an optional eligible owned project; Contact defaults to technical advice without selected variants. Sample enquiries require a validated surface. Fields, acknowledgement, validation errors and draft content are component state rather than browser storage.

With local persistence, enquiries are inserted transactionally with three outbox jobs. A scoped idempotency key + body digest returns the same reference for a repeated payload and rejects changed payloads. The form retains its retry key for an unchanged payload and ignores a response from a superseded context. The UI does not collect a shipping address or marketing opt-in. Downstream jobs contain only the enquiry ID and adapter name, never contact data in logs. Adapter implementations retrieve authorized request information server-side in production. Current adapters do not send real messages or dispatch samples.

With `VERCEL=1`, the API rejects persistence endpoints before reading contact bodies or opening SQLite. The form instead builds an editable email draft through `lib/enquiry-draft.ts`, without a network submission or contact-data storage. A separate explicit action opens the encoded mailto draft or copies its text. A long-URI fallback opens only the fixed recipient/subject and asks the user to paste the copied body. Only the email app handles a later send; the website never reports delivery. Contact details remain separate from device project drafts, share payloads, route parameters and analytics.

RBAC: editor writes draft editorial fields; technical approver reviews evidence/version/dates/rights/scope; administrator publishes a reviewed demo note and retries local jobs. Authentication uses separate private local role tokens, not trusted arbitrary request headers. Audit rows contain actor/action/record ID/time only. This is a maintainable local workflow, not a production identity provider or enterprise CMS. Least privilege, sessions/MFA, individual staff identities, signed private asset access and transactional versioned PIM imports are launch gates.

DE and EN use identical semantic path keys with locale prefix. `proxy.ts` sets the server document language; the locale switch retains the equivalent route and stable variant identifier. TR exists in the types only. No optional AI or AR code is on the core path.
